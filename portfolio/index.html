  1. 2024사일로 · 스냅픽셀

    묻고, 내가 적용한다

    사일로에서 「스냅픽셀」(Unity)을 개발하던 시기입니다. AI는 검색 대신 질문하는 상대였습니다. 변수명과 함수명을 정할 때, 짧은 함수를 짤 때, 알고리즘이 막혔을 때 해결 방향을 물었고, 받은 답이 맞는지는 제가 판단해서 코드에 옮겼습니다.

    AI가 한 일
    변수·함수 이름 제안, 짧은 함수, 알고리즘 접근법
    내가 한 일
    설계, 구현, 적용 여부 판단, 디버깅
    한계
    프로젝트 코드를 보지 못해 맥락 없이 답함
  2. 2024 – 2025Unity · MCP / CLI

    AI가 프로젝트 안으로 들어오다

    MCP와 CLI로 AI가 프로젝트 파일을 직접 읽고 쓸 수 있게 되었습니다. 이때 Unity에서 미니게임 UI 구조를 만들었습니다. 공통 UI 틀을 먼저 설계하고, 여러 미니게임이 그 틀 위에 화면만 얹어 범용적으로 쓰도록 했습니다. 당시 AI는 복잡한 문제를 풀지 못했기 때문에, 정해진 틀을 따라가는 UI 작업처럼 범위가 분명한 일만 맡겼습니다.

    AI가 한 일
    공통 틀에 맞춘 미니게임 UI 화면과 연결 코드
    내가 한 일
    범용 미니게임 UI 구조 설계, 복잡한 로직 구현
    한계
    여러 파일에 걸친 복잡한 문제는 해결하지 못함
    같은 시기 개인 Unity 프로젝트 Sathla: UnityHFSM 기반 NPC 추적·공격 AI, partial 클래스로 나눈 인게임 상태 관리
  3. 2026 상반기구현을 AI에게

    질문이 바뀌다: 어떻게 짜지 → 어떻게 맡기지

    모델이 복잡한 문제를 풀 수 있게 되면서 구현 자체를 AI에게 맡기기 시작했습니다. 고민도 "이걸 어떻게 짜지?"에서 "AI가 덜 헤매고 정확하게 짜게 하려면 무엇을 줘야 하지?"로 바뀌었습니다. 답은 문서였습니다. 세션마다 같은 맥락에서 출발하도록 .md 파일을 만들었습니다.

    AI가 한 일

    내가 한 일

Case Study

모바일 아웃게임 최적화

사일로에서 Godot 4로 개발 중인 모바일 게임의 로비 렌더링 비용을 줄인 기록입니다. 회사 프로젝트라 코드 대신 구조만 적었고, 수치는 모두 커밋에 남긴 측정 기록에서 가져왔습니다. 최적화는 아직 진행 중입니다.

목표로비 60 FPS (테스트는 120 FPS로 진행해 발열과 여유를 확보)최소 사양iPhone XR (iOS 18.7) · Android 11측정 기기Galaxy S23 Ultra (Adreno 740)

CASE 01 · 2026.10

다시 합성하는 프레임의 Draw · 재사용 프레임은 18
PROBLEM
30 FPS 배경 영상 위에 굴절·분광 효과가 들어간 유리 질감 UI가 화면 전체에 깔리는 로비에서, 120 FPS 요청 시 120이 나오지 않았습니다.
CAUSE
  • 영상은 4프레임에 1번만 바뀌는데 유리 UI 전체를 매 프레임 다시 계산
  • 불투명한 합성 결과에 가려져 안 보이는 배경 영상 변환 draw, blur가 0일 때 아무것도 바꾸지 않는 전체 화면 blur 패스와 화면 캡처가 매 프레임 실행
  • 120Hz를 요청해도 기기 설정에 따라 60Hz로 남는 경우가 있어, 요청값만으로는 결과를 알 수 없음
OPTIONS
  • 합성 결과를 버퍼에 두고 바뀔 때만 다시 그리기 → 채택
  • 호환되는 draw 묶기 → 채택. GPU 이득은 확인되지 않아 CPU 제출 비용 감소로만 기록
  • 해상도·blur·샘플 수·정밀도 낮추기 → 품질이 떨어져 쓰지 않음
  • 겹치지 않는 그림 순서 바꾸기, 라벨 Z 정렬 → 측정해 보니 비용 이득이 유지되지 않아 폐기
BUILD
  • 먼저 계측: 화면 안 성능 HUD(1초 FPS, 최악 프레임 간격, 렌더 CPU·GPU, Draw), 60 고정 / 120 요청 전환, 10분 지속 테스트. "요청한 값"과 "실제 표시 FPS"를 따로 표시
  • 유리 UI 전체를 오프스크린 버퍼 한 장에 합성하고, 영상 새 프레임·터치·설정·화면 크기 변경 때만 다시 그림
  • 가려진 영상 draw 생략, blur 0이면 blur 패스와 캡처 생략
  • 셰이더: 가장자리가 아닌 픽셀은 실루엣 계산 생략, 투명 픽셀은 굴절 계산 전에 종료. 전후 픽셀이 바이트 단위로 같은지 검사
영상 새 프레임 · 입력

변화 없음

RESULT
  • 셰이더 조기 종료: 같은 APK로 2회 비교(회당 600샘플), 렌더 GPU 8.30 → 7.77ms, 8.48 → 7.87ms, 제출 FPS 91 → 97
  • 현재: 120 요청 30초 측정 평균 약 98 FPS, 95%의 프레임이 16.67ms(60 FPS 간격) 안에 표시. 120 유지는 아직 달성하지 못했습니다.
CASE 02 · 2026.08 – 09

같은 연출을 더 싼 방법으로

4096×2048→2048×2048
UI 아틀라스 · 텍스처 메모리 절반
3.47→1.58MB
아틀라스 PNG 크기
PROBLEM
로비에서 전체 화면 배경 왜곡 셰이더, 카드마다 붙은 광택 셰이더, 홀로그램 셰이더, 마스크 셰이더가 함께 돌고 있었고, UI 아틀라스는 4096×2048까지 커져 있었습니다.
CAUSE
  • 연출마다 픽셀 단위 셰이더 계산(삼각함수, exp·pow)과 카드별 머티리얼이 붙어 있음
  • 스크롤 마스크는 스크롤 이벤트마다 마스크 이미지를 새로 만들어 업로드
OPTIONS
  • 카드 광택을 셰이더가 들어간 순차 스프라이트 효과로 → 3분 만에 되돌림
  • 부드러운 마스크용 외부 모듈 복원 → 같은 날 되돌림
  • 연출은 유지하고 애니메이션·텍스처 조회로 교체 → 채택
BUILD
  • 배경 흐름: 셰이더 → 이미지 2장의 이동·회전·크로스페이드 (9초 루프, 이음매 없음). 겹쳐 그리는 레이어가 1장 늘어나는 비용은 감수
  • 카드 광택: 카드별 셰이더 머티리얼 → 빛 줄기 이미지 애니메이션
  • 홀로그램: 픽셀마다 cos 3회 → 그라디언트 텍스처 조회 1회, 기울이지 않으면 동적 광원 계산 생략
  • 스크롤 마스크: 한 번만 준비, 갱신은 프레임당 1회, 위치가 같으면 생략. 이후 마스크 셰이더 삭제
  • XP 패스 목록: 셀 12개를 재사용하는 풀로 다시 만들고 전용 아틀라스 삭제
RESULT
UI 아틀라스 면적과 텍스처 메모리를 절반으로 줄였고, 셰이더 4종을 없애거나 단순화했습니다.

How I Work With AI

AI와 일할 때 지키는 것

규칙은 한곳에

규칙은 기준 문서 하나에 두고, 도구별 설정 파일은 그 문서를 가리키게만 합니다. 어떤 에이전트를 써도 같은 규칙을 읽습니다.

범위를 정해서 맡긴다

작업마다 계약 문서를 두고, 읽을 문서와 고칠 수 있는 파일을 정합니다. 병렬 작업의 쓰기 범위가 겹치면 시작 전에 막습니다.

끝은 실행으로 확인

"구현했다"는 말 대신 headless 테스트, 실제 재생, 결정론적 시뮬레이션 결과로 완료를 판단합니다.

엔진도 AI 기준으로 고른다

AI가 직접 읽고, 고치고, 실행해 확인할 수 있는지를 엔진과 도구 선택의 기준으로 봅니다. 그래서 지금은 Godot을 쓰고, Unity는 MCP를 검증한 뒤 돌아갈 계획입니다.

되돌리기 어려운 건 사람이

AI는 읽고 제안합니다. 실제 데이터를 바꾸는 단계는 미리보기를 거쳐 사람이 승인한 뒤에만 적용합니다.
